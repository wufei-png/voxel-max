#### ChatGPT:

我先核对 `hatch-pet` 的当前内容、它实际覆盖的生成链路，以及是否还需要额外的帧一致性、导出和表情包格式技能。然后给出最小可用组合和更稳妥的工程化方案。已经可以确定：`hatch-pet` 不是通用“任意表情包生成”技能，而是一个强约束的 **Codex 宠物精灵图流水线**。它最有价值的部分是帧一致性、确定性拼图、透明背景验证和逐行修复，但输出规格被固定为 8×9 atlas 与 `pet.json`。对一般表情包，`hatch-pet` 更适合作为**模板拆解**，而不是原样安装后直接使用。下一步关键是保留它的“基准角色→动作条→切帧→视觉 QA→导出”结构，去掉 Codex Pet 专属的 9 个状态、固定画布和 `pet.json`。

## 结论

**`hatch-pet` 是目前最值得参考的官方范例，但只在“制作 Codex 动画宠物”时适合直接使用。**

你的真实目标如果是：

> 一张角色静态图 + 动作提示词 → 多帧动画序列 → GIF / WebP / APNG / 平台表情包

最合适的方案不是原样安装 `hatch-pet`，而是：

> **参考 `hatch-pet` 的流水线，改造成自己的 `animated-sticker-maker` 本地 skill。**

一次性制作可以直接让 Codex 执行；预计反复做多个表情或一整套表情包时，才值得封装 skill。

### 本项目采用的落地顺序

Voxel Max 不先凭设想写完整 Skill，也不等 8 张全部做完才总结流程，而是采用“两个先行表情 + 同步演进”：

1. 先手工跑通 S01“收到”和 S08“被 Bug 压扁”。
2. S01 覆盖文字后置合成、眼形切换和叙事时序；S08 覆盖大幅形变、交互物分层和透明边缘。
3. 两张都形成可导出成品后，把已经证明可重复的步骤抽成仓库内 `.agents/skills/animated-sticker-maker/`。
4. 使用该 Skill 制作剩余 6 张，随着真实失败同步补脚本、QA 和修复路径。
5. 8 张完成后固化为项目 v1；经过第二个独立表情包验证后，再考虑提升为个人 Skill 或 Plugin。

这意味着 Skill 和表情包是同步优化关系，但以两张真实成品作为第一次抽象边界。

项目源资产统一采用“透明主体 + 独立阴影层”：v6 白底图只作身份参考，动作关键帧在纯洋红工作底上生成，确定性去底后保存 RGBA PNG；不依赖模型直接生成透明通道，也不把生成式地面阴影烘焙进每一帧。

### 对外最小输入契约

公开 Skill 只要求两个输入：

1. 一张静态参考图。
2. 一段自然语言提示词，描述希望发生的表情、动作、文字、循环或目标平台。

用户不需要预先提供动作卡、遮罩、角色清单、关键帧 JSON、背景颜色或平台配置。Skill 在内部完成：

```text
静态图 + 提示词
→ 主体与身份锚点分析
→ 内部动作卡
→ 锚点帧与确定性变化分工
→ 工作底选择与透明化
→ 帧序列、循环和视觉 QA
→ 通用预览或指定平台导出
```

提示词没有指定平台或技术参数时使用可移植默认值；只有语义分支会显著改变成品时才向用户追问。

默认输出只在顶层交付 `sticker.webp`；RGBA 源帧和动作计划进入 `source/`，contact sheet 与检查结果进入 `qa/`，平台特定文件进入按需创建的 `exports/<platform>/`。默认不额外生成 `preview.gif`，GIF 只在用户或平台明确需要时导出。

平台未指定时，RGBA 源帧和 `sticker.webp` 使用同一 `1024×1024` 母版画布；默认不为了预览提前缩到 512。所有缩放和体积压缩都属于平台导出层。

默认动画不固定为视频式帧率，而是使用 `4～8` 个独特帧和逐帧 `duration_ms`；总时长约 `1.2～2.0 秒`，语义终态停留约 `400～700 ms`，默认循环。

### 通用性边界

- v1 支持人物、宠物、吉祥物、插画、物体和 Logo，但要求一个明确主主体。
- 复杂背景可以先做主体提取；多主体图片必须由提示词指定目标，否则只追问这一项。
- 多人互动、完整场景动画和镜头运动不属于 v1 的稳定承诺。
- 不写死 Voxel Max 的造型、动作、配色或文字。
- v1 只正式接入 `$imagegen`，不提前实现多个未验证后端。
- 切帧、透明处理、合成、循环、QA 和导出保持后端无关。
- 工作底颜色根据主体调色板选择，不能把洋红写成所有角色的固定要求。
- 项目动作卡作为测试案例，不成为公开调用的必填参数。

## `hatch-pet` 到底做了什么

它本身**不是新的生图模型**。它把视觉生成委托给系统 `$imagegen`，自己负责：

- 锁定角色基准图
- 为每种动作生成帧条
- 提供布局参考图
- 切分帧
- 统一透明背景和尺寸
- 检查角色一致性
- 生成 contact sheet 和 GIF 预览
- 修复失败的单行动作
- 拼成固定 spritesheet
- 输出 `pet.json`

也就是说，它真正有价值的是**生产流程和确定性后处理**，不是某个特殊的“连续帧模型”。

它采用的核心结构很适合表情包：

```text
静态参考图
  ↓
canonical-base：锁定角色身份
  ↓
每种动作生成一个多帧横条
  ↓
切分透明帧
  ↓
检查体型、脸、颜色、比例、基线
  ↓
生成 GIF/WebP 预览
  ↓
仅重新生成失败动作
  ↓
最终打包
```

尤其值得保留的是：

1. **每个动作单独生成一行**，而不是一次生成整个巨大表情包。
2. 每行同时输入“角色基准图 + 帧布局 guide”。
3. 角色脸型、标记、配色、材质、道具作为 identity lock。
4. 生成后使用代码切帧和拼图，不让生图模型承担精确像素布局。
5. 先看 contact sheet，再看逐动作 GIF。
6. 某一行动作失败时，只修这一行。

## 为什么不建议原样用于表情包

`hatch-pet` 被严格绑定到 Codex Pet 协议：

| 项目     | `hatch-pet` 固定要求            | 普通表情包需求            |
| -------- | ------------------------------- | ------------------------- |
| 动作     | 9 个 Codex 状态                 | 自定义开心、震惊、催促等  |
| 布局     | 8 列 × 9 行                     | 每个表情独立文件更常见    |
| 单元尺寸 | 192×208                         | 根据平台决定              |
| 总画布   | 1536×1872                       | 通常不需要                |
| 输出     | `spritesheet.webp` + `pet.json` | GIF、APNG、WebP、PNG 序列 |
| 文字     | 默认禁止                        | 表情包经常需要文字        |
| 特效     | 严格限制浮动特效、阴影、光晕    | 表情包可以适当使用        |
| 状态语义 | idle、running、review 等        | 表情语义完全不同          |

它的固定 atlas 是 8×9，每个 cell 为 192×208，并规定了每行动作和时长。

当前官方 Codex Pet 上传也要求透明 PNG/WebP、精确 1536×1872，所以这些约束对 Pet 是正确的，但对普通表情包没有必要。([ChatGPT 学习中心](https://learn.chatgpt.com/codex/pets))

**不需要额外安装 skill。**

只有涉及这些内容时才考虑 Remotion：

## 最合理的生成策略

不要要求模型：

> “生成连续的 12 张图。”

这种提示通常不能可靠约束帧数、人物比例和运动轨迹。

更稳的是让 Codex先生成明确的动作规划：

```text
动作：角色震惊后裂开

帧 1：正常站立
帧 2：眼睛快速睁大
帧 3：身体向后缩
帧 4：头顶出现第一条裂纹
帧 5：裂纹扩展到身体
帧 6：身体分成三块
帧 7：碎块稍微向外弹开
帧 8：回弹并重新组合
```

然后一次生成一个 8 帧横向 strip：

```text
[角色基准图]
+
[8 格布局 guide]
+
[逐帧动作说明]
```

这种“**一动作一横条**”正是 `hatch-pet` 最值得借鉴的设计。它通常比以下两种方式可靠：

- 8 次完全独立生图：角色容易漂移。
- 一次生成整套几十个动作：布局和语义容易混乱。

---

## “连续帧”需要分两类理解

### 表情包式连续

6-12 张关键帧，通过停顿、回弹、循环形成动画。

这是 GPT 图像生成最适合的方式，`hatch-pet` 也是这一类。

### 视频式连续

需要非常平滑的肢体轨迹、24 fps 或更高帧率。

仅靠逐帧图像生成不理想。更合理的是：

```text
GPT 生成 4-8 张高质量关键帧
→ FILM / RIFE 插帧
→ 去除异常中间帧
→ 降到表情包所需帧率
```

但插帧容易扭曲眼睛、手指、文字和像素轮廓，所以表情包通常不需要追求视频级帧率。

| Skill                       | 输入输出                                           | 与目标的匹配度 | 主要问题                                            |
| --------------------------- | -------------------------------------------------- | -------------: | --------------------------------------------------- |

| 美图 `meitu-stickers`       | 单张照片 → 2×2 表情包 → 切成 4 张 → 可选全部转 GIF |           很高 | 依赖美图 API，动画控制较粗，不是严格逐帧生产        |

### 1. MiniMax 官方已经有直接命中的 Skill

`MiniMax-AI/skills` 中存在 MIT 许可的 `gif-sticker-maker`。它明确声明：

- 输入人物、宠物、物体或 Logo 照片；
- 生成 4 张带字幕的静态贴纸；
- 把每张图片送入 image-to-video；
- 再通过 FFmpeg 转成 4 个 GIF。

因此，从功能定义上看，它已经非常接近：

> 一张图 → 一组动态表情包。

这不是零散社区 Demo，而是 MiniMax 官方仓库列出的 Official Skill；仓库目前处于 Beta，并明确支持 Codex 安装。

但它还不能算通用生产级方案：

- 固定输出 4 张；
- 固定 Funko Pop / Pop Mart 3D 风格；
- 固定挥手、大笑、哭泣、比心四类动作；
- 使用白色背景，而非可靠透明通道；
- 人物才能使用 subject reference，动物、物体和 Logo 主要依赖文字描述；
- 没有角色一致性评分、循环检查、动作语义检查或失败帧自动修复。

它实际上是：

```text
参考照片
→ 重新设计四张静态贴纸
→ 每张静态贴纸分别做 6 秒视频
→ 视频压成 GIF
```

而不是：

```text
精确保留原静态角色
→ 规划关键帧
→ 生成低帧率表情动画
→ 自动检查并修复
→ 输出各平台合规格式
```

### 2. 美图也已经有更接近“表情包套装”的 Skill

`meitu/meitu-skills` 中的 `meitu-stickers` 接收单张主体照片，生成 2×2 四宫格，支持 Q 版、黏土、像素、Emoji 和自定义风格；确认后切成 4 张独立贴纸，还能把指定贴纸或全部贴纸转成动态 GIF。

它甚至包含：

- 单图和多图分类；
- 风格选择；
- 四宫格间距约束；
- 多级失败降级；
- 用户确认和最多三轮迭代；
- 切图失败后重新生成；
- 图片转视频再转 GIF。

这已经是一个完整的 Agent 工作流，而不只是几句 prompt。美图官方仓库也将其描述为“照片生成 2×2 表情包、拆分为四张、可选转换动态 GIF”。([GitHub](https://github.com/meitu/meitu-skills))

不过它仍然偏“调用美图 OpenAPI 的场景路由”，而不是一个通用动画表情基础设施：

- 静态表情先生成四宫格，容易出现格子间角色漂移；
- 动画阶段只使用较笼统的“执行简单、可循环表情动作”提示；
- 没有明确的关键帧规划；
- 没有基线抖动、大小跳变、脸部漂移、循环接缝等自动检测；
- 输出以 GIF 为中心，没有完整的平台适配矩阵。

## 所以这是“稀缺方向”，不是“空白方向”

可以从四个层次判断：

### Agent Skill 层

**不是空白。**

至少已有 MiniMax、美图和 OpenAI Hatch Pet 三条公开路线。GitHub 搜索中还有不少镜像、二次收录和仅负责 GIF 后处理的 Skill，但独立完整实现数量确实不多。

### 模型和算法层

**也不是空白。**

已有专门研究“静态贴纸 + 文本提示 → 多帧动态贴纸”的视频扩散方法；相关工作还研究了两百万规模的动态贴纸数据集，以及透明动态贴纸的时序 Alpha 通道生成。这说明它已经是一个明确的研究子领域。([arXiv](https://arxiv.org/abs/2402.06088?utm_source=chatgpt.com), [arXiv](https://arxiv.org/abs/2412.08259?utm_source=chatgpt.com), [arXiv](https://arxiv.org/abs/2412.20901?utm_source=chatgpt.com))

### 完全开源、本地可运行层

**接近空缺，至少尚未成熟。**

现有两个最直接的 Skill 虽然 Skill 文件和脚本是开源的，但核心生成能力分别依赖 MiniMax API 和美图 OpenAPI。它们不是“开源模型 + 本地推理 + 开源工作流”的完整栈。

### 通用生产级 Skill 层

**这里存在明显空位。**

目前没有看到一个公认成熟的方案同时覆盖：

1. 任意静态插画、表情或角色图；
2. 任意自然语言动作；
3. 精确保留角色身份和画风；
4. 自动把动作分解成关键帧；
5. 生成真正的低帧率 Sticker，而不是简单将视频压成 GIF；
6. 透明背景及边缘时序稳定；
7. 自动检测闪烁、肢体突变、角色漂移、基线跳动；
8. 单帧或局部区间修复；
9. 无缝循环；
10. 微信、QQ、飞书、Telegram、Discord、Slack 等格式导出；
11. 可插拔 GPT Image、MiniMax、可灵、Runway、ComfyUI、本地模型等后端。

## 对这个方向最准确的定位

不应将项目定位成：

> 第一个“静态图生成动态表情包”的 Skill。

这个说法已经不成立。

更准确、也更有价值的定位是：

> **第一个较完整的、模型无关的、带角色一致性 QA 和多平台导出的动态表情包生产 Skill。**

真正可以填补的不是“调用一次 image-to-video”，而是中间的工程层：

```text
角色分析
→ 表情语义设计
→ 动作与关键帧规划
→ 后端选择
→ 多候选生成
→ 角色一致性检查
→ 时序稳定检查
→ 循环修复
→ 透明背景处理
→ 文字后置合成
→ 平台合规压缩
→ 表情包打包
```

**最终判断：这个方向并非蓝海空白，但现有实现都比较垂直和供应商绑定。做一个通用、可插拔、有视觉 QA 的版本，仍然具有明确的开源价值。**
